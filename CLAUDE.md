## Commands

```bash
npm run dev      # start dev server (Next.js + Turbopack) on localhost:3000
npm run build    # production build
npm run start    # run production build
npm run lint     # next lint (eslint.config.mjs, flat config extending next/core-web-vitals + next/typescript)
```

There is no test suite in this repo currently.

### Local setup dependencies

The app requires two external services running before `npm run dev` will work end-to-end:
- **Ollama** running locally/remotely (for both chat completion and embeddings models).
- **Supabase** project with `pgvector` enabled — run the SQL in `supabaseScripts.txt` once against the project to create the `documents` table/`match_documents` RPC, the `users` table with password hashing trigger, `verify_password` RPC, and `delete_documents_by_user` RPC. A `document_store` storage bucket is also expected (used by `src/app/api/document/route.ts`). STEP 9 (hybrid search), STEP 10 (sentence-window retrieval), STEP 11 (parent-document retrieval), STEP 12 (Graph RAG), and STEP 13 (RAPTOR) add further tables/RPCs required by those RAG modes specifically — see the "Strategies" list below.

Env vars (see `env.example`): `SUPABASE_API_KEY`, `SUPABASE_URL`, `OLLAMA_LLM_BASE_URL`, `OLLAMA_LLM_MODEL`, `OLLAMA_EMBEDDINGS_BASE_URL`, `OLLAMA_EMBEDDINGS_MODEL`. Read centrally through `src/app/utils/env.ts` — always add new env vars there rather than calling `process.env` directly elsewhere.

**Optional:** `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASEURL` — when present, every `/api/chat` request is traced via LangFuse (latency, token counts, prompt/completion per chain node). The app runs normally without them. Tracing uses the OpenTelemetry-based `@langfuse/langchain` + `@langfuse/otel` SDK (v5), not the legacy `langfuse-langchain` package — that legacy package only supports LangChain 0.3.x and is incompatible with this project's `@langchain/core` v1.x stack.

## Architecture

This is a Next.js (App Router) RAG chat app: a PDF is uploaded, chunked and embedded into Supabase/pgvector, and a chat interface answers questions grounded in the retrieved chunks, streamed back to the client.

### Request flow for chat (`/api/chat`)

`src/app/api/chat/route.ts` reads an optional `ragMode` field off the request body and dispatches to `buildRagChain(mode, filter)` from `src/app/lib/rag-strategies/index.ts` — a registry (`RAG_STRATEGIES`) mapping a `RagMode` string to a strategy builder `(filter) => RunnableSequence`, exactly as before citations existed. Unknown/missing modes fall back to `DEFAULT_RAG_MODE` (`"condense"`). The chosen mode is also added to the LangFuse trace tags (`rag-mode:<mode>`) so traces can be filtered/compared per strategy.

Strategies currently registered in `src/app/lib/rag-strategies/` are plain LangChain runnable compositions — no hand-rolled async orchestration:
- **`condense`** (default, `condense.ts`) — three-stage `RunnableSequence`: (1) `standaloneTemplate` + `llm` rewrites question+history into a standalone question, handling follow-up/pronoun references; (2) the standalone question flows through `retrieveAndBuildContext(filter)` (`rag-strategies/retrieval.ts`), a `RunnableLambda` that retrieves via `retriever(filter)` and calls `buildContext` (`src/app/utils/helpers.ts`) to number each chunk as `[Source N | Page P]`, returning `{context, sources}`; (3) `answerTemplate` + `llm` streams the final answer from `{context, question, history}`, instructed to cite chunks inline as `[Source N]`.
- **`naive`** (`naive.ts`) — control-group baseline: embeds the raw question directly with no condensing/rewriting, otherwise the same retrieve → `buildContext` → answer shape.
- **`multi-query`** (`multi-query.ts`) — `multiQueryTemplate` + `llm` generates 4 alternative phrasings of the question (history-aware so pronouns resolve), then `retrieveManyAndBuildContext(filter)` (`retrieval.ts`) fans the retriever out over `[original, ...phrasings]` via `.batch()`, dedupes the unioned chunks by `pageContent`, and builds citation context. Same answer stage as the others.
- **`hyde`** (`hyde.ts`) — HyDE (Hypothetical Document Embeddings): structurally identical to `condense`, but the first stage (`hydeTemplate` + `llm`) drafts a short *hypothetical answer passage* (history-aware) and embeds that for retrieval instead of a rewritten question — answer-shaped text lands closer to document chunks in embedding space than question-shaped text does. The draft is retrieval-only; the user-visible answer is still generated from retrieved context.
- **`hybrid`** (`hybrid.ts`) — hybrid keyword + vector search: the raw question (no rewriting, so exact terms/acronyms survive) goes through `hybridRetrieveAndBuildContext(filter)` (`retrieval.ts`) → `hybridSearcher` (`supabase.ts`), which embeds the query and calls the `hybrid_search` RPC directly — full-text (`tsvector`/GIN) and vector rankings fused in-database via reciprocal rank fusion. Bypasses `SupabaseVectorStore` because that class only sends the embedding, and hybrid needs the query *text* too. **Requires `supabaseScripts.txt` STEP 9 to have been run** — without it the RPC doesn't exist and this mode errors at query time.
- **`rerank`** (`rerank.ts`) — LLM-based re-ranking: retrieves on the raw question via `rerankRetrieveAndBuildContext(filter)` (`retrieval.ts`), over-fetching 20 candidates by cosine similarity (`retriever(filter, k)` now takes an optional `k`, passed straight to `VectorStore.asRetriever`), scores each candidate's relevance to the question with one `llm` call apiece (`rerankTemplate`, 0–1 score), sorts, and keeps the top 4. Ollama has no cross-encoder model, so this is prompt-based scoring rather than a real reranker — 20 extra LLM calls per query, so noticeably slower/costlier than the other modes; that tradeoff is the point of comparing it in LangFuse.
- **`contextual-compression`** (`contextual-compression.ts`) — retrieves on the raw question (isolating the change against `naive`) via `compressRetrieveAndBuildContext(filter)` (`retrieval.ts`), then asks an `llm` call per retrieved chunk (`compressionTemplate`) to strip out sentences irrelevant to the question, keeping the rest verbatim (falls back to the original chunk if the LLM strips everything, so a chunk never collapses to an empty, uncited source). Unlike `rerank`, which drops whole chunks, this trims *within* each kept chunk — cutting the noise the answer LLM has to read past without discarding chunks that are only partially relevant.
- **`sentence-window`** (`sentence-window.ts`) — retrieves on the raw question (isolating the change against `naive`, like `contextual-compression`) via `sentenceWindowRetrieveAndBuildContext(filter)` (`retrieval.ts`), but against a **second, sentence-granularity index**: ingestion (`api/document/route.ts`) additionally splits each page into individual sentences (`buildSentenceWindowDocuments` in `lib/sentence-window.ts`, a regex-based splitter — a documented simplification, not real NLP segmentation) and embeds each sentence on its own into a separate `sentence_documents` table, precomputing and storing a `windowText` (that sentence plus its 2 neighbors on each side) in each row's metadata. At query time the retriever matches on individual sentences — a tighter embedding than a ~1000-char chunk, since it isn't blurred across several ideas — then `expandToWindow` swaps each hit's `pageContent` for its precomputed `windowText` (deduping identical/overlapping windows from adjacent hits) before `buildContext`, so the answer LLM reads restored surrounding context instead of one bare sentence. A separate table is required, not just a metadata flag on `documents`: every retriever filters by `{userId}` alone, and Postgres jsonb containment (`@>`) is a superset match, so sentence-level rows sharing that same `userId` would otherwise leak into every other mode's retrieval. **Requires `supabaseScripts.txt` STEP 10 to have been run** — without it this mode errors at query time (same as hybrid's STEP 9 dependency). Ingestion cost tradeoff: this mode adds one embedding call per sentence in the document (on top of the existing per-chunk embeddings) and roughly doubles Supabase storage for the document — noticeably slower ingestion, the same kind of tradeoff `rerank`'s 20 extra LLM calls are for query time.
- **`parent-document`** (`parent-document.ts`) — retrieves on the raw question (isolating the change against `naive`, like `contextual-compression`/`sentence-window`) via `parentDocumentRetrieveAndBuildContext(filter)` (`retrieval.ts`), but against a **third granularity index**: ingestion (`api/document/route.ts`) additionally splits each already-split ~1000-char parent chunk into smaller 200/20 child chunks (`buildChildDocuments` in `lib/parent-document.ts`) and embeds each child on its own into a separate `child_documents` table, precomputing and storing the full `parentText` in each row's metadata. At query time the retriever matches on individual child chunks — a tighter, more narrowly-scoped embedding than the ~1000-char parent — then `expandToParent` swaps each hit's `pageContent` for its precomputed `parentText` (deduping when multiple child hits share the same parent) before `buildContext`, so the answer LLM reads the full parent chunk instead of one narrow fragment. Structurally the mirror image of `sentence-window` (same separate-table/precomputed-expansion pattern, one level up in granularity: parent chunk ↔ child chunk instead of sentence ↔ window) — same reason a separate table is required, not a metadata flag on `documents`. **Requires `supabaseScripts.txt` STEP 11 to have been run** — without it this mode errors at query time (same as hybrid's STEP 9 and sentence-window's STEP 10 dependencies). Ingestion cost tradeoff: adds one embedding call per child chunk (several per parent chunk) and roughly doubles Supabase storage — the same kind of tradeoff sentence-window's per-sentence embeddings are.
- **`auto-merging`** (`auto-merging.ts`) — retrieves on the raw question (isolating the change against `naive`, same as `parent-document`) via `autoMergeRetrieveAndBuildContext(filter)` (`retrieval.ts`), reusing `parent-document`'s **same `child_documents` table/`childRetriever`** — no new schema, no ingestion change. The difference is purely retrieval-side policy: `parent-document` always expands every hit to its full parent; `auto-merging` over-fetches more child candidates (12, via `autoMergeChunks`), groups them by shared `parentText`, and only promotes a group to the full parent chunk once at least 2 sibling children were independently retrieved (real corroborating evidence), otherwise a lone hit is kept at its own narrow child granularity rather than pulling in the whole parent on one match's strength.
- **`self-rag`** (`self-rag.ts`) — retrieves on the raw question via `selfRagRetrieveAndBuildContext(filter)` (`retrieval.ts`), which judges (0–1, `judgeSufficiency`) whether the retrieved context is actually sufficient to answer the question **before** generating; if not, and a hop remains, the question is rewritten (`selfRagRewriteTemplate`) and retrieval retried, capped at 2 hops. After the single streamed `answerLLM` call, a second, distinct LLM call (`critiqueGroundedness`) scores how well the generated answer is actually supported by the context — but only as a **reported** score, not a regenerate gate: this repo's SSE protocol assumes exactly one clean `answerLLM` token stream per response, so gating a retry on a post-hoc critique of the *generated answer* (as canonical Self-RAG does) would require a second `answerLLM` call and a duplicated/broken stream. This is a deliberate, documented simplification of Self-RAG for this architecture — same spirit as hybrid's "not real BM25" note — splitting its "critiques own answer, re-retrieves if not" idea into a pre-generation sufficiency-gated retry loop (where the capped hops genuinely apply) and a post-generation groundedness score (informational only).
- **`crag`** (`crag.ts`) — Corrective RAG: retrieves on the raw question via `cragRetrieveAndBuildContext(filter)` (`retrieval.ts`), which **reuses `rerank`'s existing `scoreCandidates`** (same over-fetch-20-then-pointwise-score approach) rather than a new scorer, but instead of just dropping low scorers it checks whether *any* candidate cleared a relevance bar; if none did, the question is rewritten (`cragRewriteTemplate`) and retrieval retried once, then the best-scoring attempt's candidates are kept. Entirely retrieval-side (no post-generation critique, unlike `self-rag`), so a single `answerLLM` call either way — no streaming complications.
- **`agentic`** (`agentic.ts`) — Agentic/router RAG: an LLM call (`routeQueryTemplate`) classifies the question into one of 3 labels — `DIRECT` (small talk/general knowledge, no retrieval), `SINGLE` (one focused retrieval), or `MULTI` (a broad/ambiguous question worth a multi-phrasing fan-out) — then a `RunnableBranch` (a first-class LangChain composition primitive, not a hand-rolled `if`/`async` dispatch) routes to a `directAnswerTemplate`-only branch, or **delegates straight to the already-exported `naiveChain`/`multiQueryChain`** for the other two, rather than re-implementing retrieval logic. Because those are real chains (not stubs), whichever branch runs still emits the same named `retrieveAndBuildContext`/`answerLLM` events `route.ts` already knows how to read — `RunnableBranch` correctly threads the parent's config through to the selected branch, so its `answerLLM` streams normally, and a `DIRECT` answer simply never fires a `retrieveAndBuildContext` event (route.ts just never emits a `sources` SSE event for that response, which is correct — there's nothing to cite). Scoped to a 3-way classification rather than a full pick across every registered mode, since reliably classifying into that many categories isn't realistic for a small local Ollama model — documented as a deliberate scope-narrowing, same spirit as hybrid's "not real BM25" note. Known UX approximation: the pipeline visualizer's persistent pre-chat stage list (`pipeline-metadata.ts`'s `agentic` entry) is necessarily the union of every branch's possible stages, since only the router's actual choice fires real `stage` events during a given chat.
- **`multi-hop`** (`multi-hop.ts`) — decomposes the question into 1-4 sub-questions (`subQuestionTemplate`; a simple/atomic question just comes back as itself, degrading gracefully to single-hop) via `decomposeQuestions`, then `retrieveMultiHopAndBuildContext(filter)` (`retrieval.ts`) fans retrieval out over the sub-questions — **reusing the exact same `{list}->Document[][]` shape and `"vectorRetrieveMany"` runName as `multi-query`'s fan-out step**, carrying the sub-questions alongside via a parallel branch (same pattern `contextual-compression`'s `compressRetrieveAndBuildContext` uses to carry the question alongside its docs). Differs from `multi-query` in how the context is built: `buildMultiHopContext` (named `"buildHopContext"`, distinct from `"dedupeCandidates"` since its output shape differs — grouped/labeled text, not a flat `Document[]`) keeps each sub-question's chunks grouped and attributed under a `"Sub-question K"` header rather than flattening every phrasing's hits into one undifferentiated deduped pool — letting the answer LLM reason across hops explicitly instead of pattern-matching a merged blob. Citation numbering/dedup still follows `buildContext`'s exact contract (global 1..N, deduped by `pageContent`).
- **`graph`** (`graph.ts`) — Graph RAG: retrieves on the raw question via `graphRetrieveAndBuildContext(filter)` (`retrieval.ts`), which wraps `graphSearcher(filter)` (`lib/graph-rag.ts`) the same way `hybrid` wraps `hybridSearcher` — bypassing `SupabaseVectorStore` since traversal needs the raw query text, not just its embedding. At ingestion (`api/document/route.ts`), one LLM call per parent chunk (`graphExtractionTemplate`, `extractGraphData`) extracts a small, best-effort JSON list of entity mentions and (source, relation, target) triples — small local models are unreliable at strict JSON, so a chunk that doesn't parse is simply skipped, same category of simplification as sentence-window's regex sentence splitter. Entity names are normalized (trimmed, lowercased) and deduped globally per document; `insertGraphData` writes them to `graph_entities`, links each to the chunks that mention it via `graph_entity_mentions`, and writes relation triples to `graph_relations` (STEP 12 in `supabaseScripts.txt` — **plain typed columns, not jsonb metadata**, since traversal needs real foreign-key joins rather than jsonb containment filtering, and there's no embedding column at all — entity matching is name-based, not vector-similarity-based). At query time, `extractQuestionEntities` (bare LLM call, lenient JSON-array parse) pulls entity names out of the question, looks them up in `graph_entities` by exact normalized name, expands one hop via `graph_relations`, collects every matched/related entity's mentioned chunks from `graph_entity_mentions`, and fetches those rows straight out of `documents` by id. **Falls back to plain vector retrieval on the raw question if no entities matched at all** (a question with no recognizable proper nouns would otherwise hit a dead-end empty context). Both the name-only matching and 1-hop-only traversal are documented simplifications of a production graph-RAG system (which would typically also embed entity names/descriptions for fuzzy matching and traverse further) — same spirit as hybrid search's "not real BM25" note. Ingestion cost tradeoff: adds one LLM call per parent chunk (extraction), on top of the existing per-chunk/child/sentence embedding calls — the same kind of tradeoff sentence-window's/parent-document's extra embedding calls are, but LLM calls rather than embedding calls.
- **`adaptive`** (`adaptive.ts`) — Adaptive RAG, the roadmap's capstone: built directly on top of two prior modules rather than reinventing retrieval logic. An LLM call (`routeComplexityTemplate`) classifies the question as `DIRECT` (no retrieval), `SIMPLE` (one focused retrieval), or `COMPOUND` (worth splitting into sub-questions), then the same `RunnableBranch` dispatch pattern `agentic.ts` uses delegates to a `DIRECT`-only branch, or straight to the already-exported `naiveChain`/`multiHopChain` for the other two. Deliberately kept as its own small file rather than merged with `agentic.ts` into one parameterized router (per this repo's anti-abstraction guidance) — the two routers classify by a genuinely different axis (complexity here vs. retrieval mechanism there) even though the branch-dispatch plumbing looks similar. Same known UX approximation as `agentic`: the pipeline visualizer's persistent pre-chat stage list is the union of every branch's possible stages, since only the router's actual choice fires real `stage` events during a given chat.
- **`rag-fusion`** (`rag-fusion.ts`) — RAG-Fusion: reuses `multi-query`'s exported `rephraseChain` (same 4 phrasings) and same `"vectorRetrieveMany"` fan-out (6 per phrasing), but `ragFusionRetrieveAndBuildContext` (`retrieval.ts`) merges the per-phrasing ranked lists with reciprocal rank fusion (`fuseRankings`, `1/(60+rank)` summed across lists, top 4 kept) instead of dedupe-and-concatenate. The 4-chunk trim keeps the isolated variable against `multi-query` the fusion step, not a bigger context. Same fusion math as `hybrid`'s in-database RRF, applied across query variants rather than search types.
- **`speculative`** (`speculative.ts`) — Speculative RAG: retrieves a 12-chunk pool on the raw question, splits it into 3 subsets round-robin by rank, drafts an answer from each subset and has a verifier score each draft (`speculativeSelect`, stage `speculativeDrafts`); the best draft's *subset* becomes the context for the single streamed `answerLLM` call. **Deliberate simplification**: canonical Speculative RAG returns the winning draft itself as the answer, but this repo's SSE protocol assumes exactly one clean `answerLLM` token stream per response (same constraint as `self-rag`), so drafts are used to *select evidence* and the answer is regenerated from it. Cost: 3 drafts + 3 verifier calls per query. Drafts/verifier prompts ride along as `StageRow` data (bare `.invoke()`, never enters the traced graph — same as `rerank`).
- **`flare`** (`flare.ts`) — FLARE (Forward-Looking Active Retrieval), adapted: `flareDraft` (history-aware tentative answer from general knowledge, LLM inner runName `flareDraftLLM`) → `flareLookahead` (`retrieval.ts`) splits the draft into ≤4 sentences, scores the model's verbalized confidence in each, and retrieves with the sentence itself as the query for every one below 0.7, alongside the question's own retrieval (always run — a grounded answer needs context even if the draft looked confident) → deduped union → `answerLLM`. **Deliberate simplification**: canonical FLARE triggers retrieval on low token probability *while streaming the final answer*, which is incompatible with the one-clean-stream protocol (and Ollama logprobs aren't reliable across models), so lookahead happens up-front over a tentative draft with verbalized confidence standing in for token probability. Same "documented simplification" spirit as `self-rag`.
- **`raptor`** (`raptor.ts`) — RAPTOR: at ingestion (`api/document/route.ts` → `buildRaptorTree` in `lib/raptor.ts`) the ~1000-char parent chunks are clustered by embedding (deterministic cosine k-means, ~5 per cluster, `clusterVectors`), each cluster is LLM-summarized (`raptorSummaryTemplate`), and the summaries are clustered and summarized again, up to 3 levels. Only the **summary nodes** are stored, in a separate `raptor_documents` table (**STEP 13** in `supabaseScripts.txt`, same separate-table reasoning as sentence-window/parent-document; leaves are just the existing `documents` rows). At query time `raptorRetrieveAndBuildContext` retrieves 3 leaves (reusing the `"vectorRetrieve"` runName) and 2 summaries (`"raptorSummaryRetrieve"`) in a parallel branch and `mergeTreeLevels` interleaves them, labeling each summary `[Section summary, pages a-b]` (a summary's citation page is its earliest member page). Simplifications vs. the paper: k-means instead of UMAP + Gaussian mixture models (no soft multi-cluster membership), and interleaving instead of ranking all nodes in one similarity pool (the retriever doesn't expose scores). **Requires STEP 13 and a re-upload of the document** — without them this mode errors at query time (same dependency pattern as hybrid/sentence-window/parent-document/graph). Ingestion cost: the heaviest of any mode — one extra embedding pass over the leaves (clustering needs vectors, and `SupabaseVectorStore` doesn't return them) plus ~N/5 + N/25 + … summarization LLM calls. Registered in `CHUNK_INDEXES`/`CHUNK_STRATEGY_META` for the Chunks viewer.

`retrieveAndBuildContext` / `retrieveManyAndBuildContext` (shared by the strategies — the multi-query variant deliberately carries the **same** `runName` `"retrieveAndBuildContext"` so the route's `sources` extraction is strategy-agnostic) and the final answer LLM call are each given an explicit `runName` (`"retrieveAndBuildContext"` and `"answerLLM"`) via `.withConfig({runName})`. This is purely so `/api/chat` can pick their events out of `.streamEvents()` by name — it has no effect on chain behavior.

`src/app/lib/rag-strategies/modes.ts` holds the `RagMode` type and UI labels and has **no LangChain/LLM imports** so it can be safely imported from client components (see `src/app/home/page.tsx`'s mode picker) — everything else in that folder is server-only.

Prompt text lives in `src/app/lib/prompts.ts` — edit these templates to change model behavior/tone, not the runnable wiring. Add a new RAG technique by adding a strategy file (a `RunnableSequence` factory, typically built around `retrieveAndBuildContext`) + registering it in both `rag-strategies/index.ts` (`RAG_STRATEGIES`) and `rag-strategies/modes.ts` (`RAG_MODES`, for the UI picker).

### Streaming protocol and source citations

`/api/chat` calls `chain.streamEvents(input, {version: "v2", callbacks})` rather than `chain.stream()`, and responds with `Content-Type: text/event-stream` (SSE) rather than raw text — this is what lets the response carry a structured `sources` payload alongside the answer tokens without changing the strategy chains into anything other than plain runnables. The route filters the raw LangChain event stream down to four SSE event types: one `sources` event (the `on_chain_end` output of the `retrieveAndBuildContext` step — a JSON array of `{id, pageNumber}`, emitted before any tokens because that step finishes before the answer LLM starts generating), one `token` event per `on_chat_model_stream` chunk from the step named `answerLLM` (`{text: "..."}`), `stage` events (see below), then a terminal `done` (or `error`) event. The frontend (`src/app/home/page.tsx`) hand-parses this over a raw `fetch` + `ReadableStream` reader (splitting on blank lines) rather than using `EventSource`, because `EventSource` can't send the POST body/custom headers this route needs.

### Pipeline visualizer (`stage` SSE events)

Every strategy names its internal sub-steps via `.withConfig({runName})` (not just the shared `retrieveAndBuildContext`/`answerLLM` pair) — e.g. `condense.ts`'s standalone-question rewrite is named `standaloneQuestion`, `multi-query.ts`'s rephrasing step is `generatePhrasings`, `hyde.ts`'s draft is `hydeDraft`, and `retrieval.ts`'s retriever/dedupe/rerank/compression/expansion sub-steps are named `vectorRetrieve`/`vectorRetrieveMany`/`dedupeCandidates`/`hybridSearch`/`overFetchCandidates`/`scoreCandidates`/`compressChunks`/`expandWindow`/`expandToParent`. `src/app/lib/rag-strategies/pipeline-metadata.ts` (client-safe, like `modes.ts`) declares, per `RagMode`, the ordered list of these stage ids plus newbie-facing `label`/`what`/`why` text — this is the single source of truth both the backend and frontend key off of. `/api/chat/route.ts` builds a `STAGE_IDS` set from it and, independently of the `sources`/`token` emission, emits one `stage` SSE event per `on_*_start`/`on_*_end` LangChain event whose `event.name` is a known stage id (matched generically by event-type suffix since retriever/chat-model/chain runnables emit different `on_*` prefixes for the same concept) — `{stageId, status: "start"|"end", data?}`, where `data` (on `end` only) is `{input, output, llm?}`: `input`/`output` are small display-shaped payloads from `shapeStageInput()`/`shapeStageData()` (the literal text/query sent into and the doc/chunk previews, phrasings list, or rerank score table that came out), and `llm` (only for `standaloneQuestion`/`generatePhrasings`/`hydeDraft`/`answerLLM`) is `{prompt, completion}` — the literal rendered prompt text and raw completion, reconstructed from the nested `on_chat_model_end` event's `{messages}` input. The three query-transformation stages wrap their inner LLM call in a *second*, distinctly-named runnable (`standaloneQuestionLLM`/`generatePhrasingsLLM`/`hydeDraftLLM` — see `LLM_STAGE_RUNNAMES` in `route.ts`) purely so that inner call's own start/end events don't collide with the outer stage's own same-named start/end events; `answerLLM` needs no such split since it *is* the chat-model call directly (no wrapping sequence). Note: LangChain JS's `StreamEvent` type has no `parent_ids` field (unlike the Python version), so nested events can only be attributed to a parent stage by giving them distinct names — don't assume run-id/parent-id correlation is available if extending this further. `rerank.ts`'s 20 per-candidate scoring calls (`scoreRelevance` in `retrieval.ts`) are a sharper version of the same problem: they run via a bare `.invoke()` with no `RunnableConfig`/callbacks threaded through from the parent chain, so they never enter the traced execution graph at all — no runName would ever make them appear in `chain.streamEvents()`. Their prompt/completion is instead captured directly as plain data inside `scoreRelevance`/`scoreCandidates` (via `rerankTemplate.format()` for the prompt) and carried out as extra fields (`prompt`, `completion`) on each `ScoredCandidate` row, rendered as a per-row expandable disclosure in `RagPipelineVisualizer.tsx`'s score table — a different mechanism from the single `llm: {prompt, completion}` field used for the other LLM stages. `contextual-compression.ts`'s per-chunk compression calls (`compressChunk`/`compressCandidates` in `retrieval.ts`) follow the exact same direct-capture pattern (via `compressionTemplate.format()`), carried as `prompt`/`completion` on each `CompressedChunk` row. The frontend's `RagPipelineVisualizer` component (`src/app/components/RagPipelineVisualizer.tsx`) renders `RAG_PIPELINE_STAGES[mode]` as a step-by-step diagram — pending/active/done per stage, with a collapsed-by-default "Show raw LLM prompt & response" disclosure per LLM stage — fed either by this live `stage` stream (mounted persistently above the message list, so any mode's pipeline is browsable before a question is even sent) or, per assistant message, by that message's frozen `pipelineTrace` (captured in `home/page.tsx`'s SSE loop the same way `sources` is) behind a "How this answer was generated" toggle.

The LLM is prompted (`answerTemplate` in `prompts.ts`) to cite chunks inline as `[Source N]`; the client turns those into clickable markdown links (`linkifyCitations` in `home/page.tsx`) that look up that source's `pageNumber` and jump the embedded PDF viewer straight to it. Each assistant message also renders a row of "Page N" chips (deduped from its `sources`) as a citation-free fallback way to jump pages. The PDF itself is rendered via a plain `<iframe src="<blob-url>#page=N">` — no `react-pdf`/pdfjs — so it stays embedded and visible the whole time ("always open") and the browser's own PDF viewer supplies zoom/search/print/manual scroll for free. Because `<iframe>` can't send the `User-Id` auth header, the client still fetches the file with `fetch()` first and turns the response into an object URL, exactly like the pre-citation-era implementation did.

### Document ingestion flow (`/api/document`)

`POST` — uploads the raw PDF to a Supabase Storage bucket (`document_store`, keyed by `${userId}.${ext}`, one file per user, `upsert: true`), parses it with `PDFLoader`, splits it with `RecursiveCharacterTextSplitter` (1000/100 chunk size/overlap), tags each chunk with `{documentName, pageNumber, userId}` metadata, deletes that user's previous embeddings (`delete_documents_by_user` RPC) before writing new ones, then embeds and stores via `vectorStore().addDocuments`. It also dual-writes a sentence-granularity index for the `sentence-window` RAG mode: `buildSentenceWindowDocuments` (`lib/sentence-window.ts`) splits each page into sentences with a precomputed neighboring-sentence `windowText` per sentence, that set is deleted (`delete_sentence_documents_by_user` RPC) and re-embedded into the separate `sentence_documents` table via `sentenceVectorStore().addDocuments` — see the `sentence-window` bullet above for why this needs its own table. It additionally dual-writes a child-chunk index for the `parent-document` RAG mode: `buildChildDocuments` (`lib/parent-document.ts`) further splits each already-split ~1000-char parent chunk into 200/20 child chunks, tagging each with the full `parentText`; that set is deleted (`delete_child_documents_by_user` RPC) and re-embedded into the separate `child_documents` table via `childVectorStore().addDocuments` — see the `parent-document` bullet above for why this needs its own table. It also extracts an entity/relation graph for the `graph` RAG mode: after the parent chunks are inserted (their `documents.id` values are only known at that point), `extractGraphData` (`lib/graph-rag.ts`) runs one LLM call per parent chunk to pull out entities/relations, old graph rows are deleted (`delete_graph_data_by_user` RPC), and `insertGraphData` writes the new `graph_entities`/`graph_entity_mentions`/`graph_relations` rows — see the `graph` bullet above. Finally it builds the RAPTOR summary tree for the `raptor` mode: `buildRaptorTree` (`lib/raptor.ts`) clusters the parent chunks by embedding, LLM-summarizes each cluster recursively (up to 3 levels), the old summaries are deleted first (`delete_raptor_documents_by_user` RPC) and the new summary nodes are written to `raptor_documents` via `raptorVectorStore().addVectors` (vectors already computed while clustering, so nothing is embedded twice) — see the `raptor` bullet above.

`GET` — looks up the current user's stored file by name prefix and streams it back; the client wraps it in an object URL for the embedded `<iframe>` PDF viewer.

Because storage/retrieval is scoped by `userId` header (not real auth), each user effectively has exactly one active document at a time.

### Auth model — important gotcha

Login/signup (`/api/login`, `/api/signup`) hit Supabase RPCs (`verify_password`, raw `insert` into `users`) directly with **no session/JWT issued**. The client (`src/app/page.tsx`) just stores the plaintext `username` in `sessionStorage.userId` on success and sends it back as the `User-Id` header on every subsequent `/api/chat` and `/api/document` request — that header is the sole "auth" boundary and is trivially spoofable. `jose` and `@types/jsonwebtoken` are in `package.json` but are not currently wired into any route — don't assume JWT-based auth exists when reading or modifying auth code.

## Evaluation (Phase 2)

`npm run eval` (`scripts/eval.ts`) runs every registered `RagMode` (from `RAG_MODES` in `rag-strategies/modes.ts`) against a small fixed golden question set (`src/app/lib/eval/goldenSet.ts`, 10 questions written specifically about "Attention Is All You Need" — `EVAL_DOCUMENT` names it) and scores each answer with [raglens](https://github.com/AbhisekMishra/raglens) (`faithfulness`, `answer_relevancy`, `context_precision`, `context_recall` — the last two need raglens ≥0.2), printing a per-mode comparison table. **Prerequisite**: that PDF must already be uploaded under whichever `userId` the script is pointed at (`--userId=<id>`, defaults to `"eval-user"`) — re-upload it via `POST /api/document` with that `User-Id` header before running. Requires `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` in `.env` for score-pushing (optional — scores are still computed and printed without it, same as chat tracing).
- **Judge model**: `OLLAMA_JUDGE_MODEL` (optional env var, `env.ts`) lets the judge be a separate, ideally larger/more capable model than whichever one answered the questions — falls back to `OLLAMA_LLM_MODEL` when unset, meaning the model judges its own answers (a real bias, only partially mitigated by using a separate model since it's still self-consistency-prone rather than a fully independent evaluation). Same Ollama base URL as the chat model — no separate judge server assumed.

- **Resuming / subsetting**: `npm run eval -- --modes=auto-merging,self-rag` runs only those modes. A mode that exhausts its retries is recorded as `FAILED` in the final table and the run continues, rather than aborting every other mode's results.
- **LangFuse Dataset + experiments (Phase 3)**: `npm run langfuse:sync` upserts the golden set as dataset `rag-golden-set` (deterministic item ids `golden-<index>`, `src/app/lib/eval/dataset.ts`). After scoring, `runEvalForMode` links each trace to its item via `POST /api/public/dataset-run-items` with runName `"<mode> | <runTag>"`, so LangFuse's dataset Runs view compares modes side by side. Run the sync once before `npm run eval` (a link failure only logs, scores are unaffected). REST calls go through `src/app/lib/eval/langfuseApi.ts` (same no-SDK-helper rationale as `pushScoreToLangfuse`).
- **Managed prompts (partial)**: `langfuse:sync` also pushes every `PromptTemplate` exported from `prompts.ts` as a LangFuse text prompt (kebab-case name, `{var}`→`{{var}}`, label `production`) so versions/diffs are visible there. **Runtime fetching from LangFuse is deliberately NOT wired** — chains build their templates as sync module constants, and making every strategy fetch asynchronously (with a fallback) is a larger refactor; `prompts.ts` remains the source of truth and the sync is one-way.
- `src/app/lib/eval/runEval.ts` — `runChainForEval` builds a chain via `buildRagChain` and drives it with `chain.streamEvents()` — **the same event-matching approach `api/chat/route.ts` uses** (accumulate `on_chat_model_stream` chunks named `"answerLLM"` into the answer string, capture the `"retrieveAndBuildContext"` step's `.context` output) — rather than `.invoke()`, because each mode's final chain output shape isn't uniform (`self-rag` appends a `critiqueGroundedness` step returning `{answer, groundedness}`; `agentic`/`adaptive`'s output depends on which `RunnableBranch` arm fired). A fresh `CallbackHandler` per question captures `handler.last_trace_id` (a public property) so raglens' per-metric scores can be pushed back against that exact trace.
- **`scripts/eval.ts` has to register its own LangFuse tracer provider** (`registerLangfuseTracing`, mirroring `instrumentation.ts`'s `setLangfuseTracerProvider(new NodeTracerProvider({spanProcessors:[new LangfuseSpanProcessor(...)]}))`) — `instrumentation.ts`'s own `register()` hook only fires inside the Next.js request lifecycle (`next dev`/`next start`), never for a plain script run via `tsx`. Without this, `CallbackHandler` still generates a `last_trace_id` locally, but no actual trace/span data is ever exported — `pushScoreToLangfuse` would silently attach real scores to a trace id nothing backs (this happened during initial development: scores appeared in LangFuse with correct values, but no matching trace existed until the fix). The script also `await`s `tracerProvider.shutdown()` in a `finally` block after the eval loop — a short-lived script can otherwise exit before the span processor's batched export runs, same failure mode.
- **Known gap, root-caused but not fixed, not introduced by Phase 2**: traces created via `CallbackHandler` in this project (both `api/chat/route.ts`'s live chat traces and eval's) show up in LangFuse with real input/output/observations, but `tags`/`userId` consistently land empty (`[]`/`null`) on the trace object itself even though `CallbackHandler`'s constructor is given both. Confirmed on an existing Phase-1-era live-chat trace too, so it predates Phase 2 and isn't an eval-specific bug.
  - **Root cause** (traced through `@langfuse/core`'s compiled source): `CallbackHandler.handleChainStart`, for the root LangChain call, calls `propagateAttributes({tags, userId, ...}, () => this.startAndRegisterOtelSpan(...))`. `propagateAttributes` captures `trace.getActiveSpan()` **before** `startAndRegisterOtelSpan` creates the new root span — since nothing is active yet on the very first call of a request, that lookup returns `undefined`, and the conditional `span.setAttribute(...)` branch never fires. The values are still written into the OTel Context (for potential downstream reads), but nothing downstream reads them back out, so they never reach an actual span attribute `LangfuseSpanProcessor` could export.
  - **Confirmed NOT fixed by upgrading** `@langfuse/core`/`langchain`/`otel`/`tracing` from 5.9.1 → 5.11.0 (kept the upgrade anyway — newer, no regressions, worth having).
  - **An app-level workaround was attempted and does NOT work**: wrapping chain execution in our own `startActiveObservation` span (so an active span exists before `CallbackHandler`'s internal `propagateAttributes` call fires) requires ambient OTel context propagation to work at all — which this project's `instrumentation.ts` deliberately breaks by never calling `provider.register()` on its isolated `NodeTracerProvider` (to avoid conflicting with Next.js's own global OTel provider claim). Separately registering just a `ContextManager` (`context.setGlobalContextManager(new AsyncLocalStorageContextManager().enable())`, without touching tracer-provider registration) *does* fix ambient context propagation in isolation — but `CallbackHandler` doesn't consult ambient context for its own span hierarchy anyway: it tracks parent/child spans explicitly via LangChain's own `runId`/`parentRunId` callback parameters, not `trace.getActiveSpan()`. So even with working ambient context, `CallbackHandler`'s root call still starts an independent root span/trace, oblivious to any wrapper span placed around it — confirmed by testing: two separate orphaned traces appeared (the wrapper's and `CallbackHandler`'s), neither with correct tags/userId on the one that actually has the chain's real content.
  - **Remaining real fix**: a `patch-package` hack on `@langfuse/core`'s compiled `propagateAttributes`/`CallbackHandler.handleChainStart` call ordering (patching the actual bug, at the actual place it occurs) — not attempted, since patching third-party compiled output is a real fragility/maintenance tradeoff (silently breaks on any future SDK version bump if not revisited) that deserves its own explicit decision rather than being bundled into an eval-improvement pass. Filtering traces by tag or userId in the LangFuse UI doesn't work until this happens; trace content and scores are unaffected either way.
- `pushScoreToLangfuse` in the same file does a raw `fetch()` POST to `${LANGFUSE_BASEURL}/api/public/ingestion` with HTTP Basic Auth and a `score-create` batch event — the installed LangFuse SDKs (`@langfuse/core`/`langchain`/`otel`/`tracing`, all v5.11.0) have no ergonomic score-create helper (their `Scores` class is read-only; the Fern-generated `LangfuseAPIClient` construction is ambiguous for one write call), so this hand-rolls the same stable, documented ingestion REST shape those SDKs wrap internally.
- **Self-judging caveat**: without `OLLAMA_JUDGE_MODEL` set, the eval judge (`raglens.createOllamaJudge`) uses the exact same model that generated the answers being judged — a real bias. Setting it to a separate, larger model helps but doesn't fully eliminate the concern (still one local model family's judgment, not an independent reference).
- Each `Sample`'s `contexts` is the `[Source N | Page P]`-labeled string `buildContext`/`buildMultiHopContext` produce, split back into one entry per chunk in rank order (`splitContext` in `runEval.ts`) — `context_precision` needs per-chunk rank order; the other metrics just join them. `sentence-window`/`parent-document`/`auto-merging` rank *expanded* windows/parents and `contextual-compression` ranks compressed text, so precision there reflects what the answer LLM actually saw. The two new metrics roughly double judge calls per question (precision = 1 call per chunk; recall = 1 + one per ground-truth statement).
- Cost warning: 10 questions × 20 modes × each mode's own LLM calls (several modes already cost 5-25+ extra calls per query — `rerank`, `self-rag`, `crag`, `graph`) × raglens' own judge calls (faithfulness's per-statement verification, answer_relevancy's one call) adds up fast on a local small model — a full run can take a long time; this is why the golden set stays small rather than growing it casually.

Follow-up run 2026-09-30 of the four-metric harness on the three newly added modes that need no new schema (same setup): `rag-fusion` 0.81 faith. / 0.71 rel. / 0.90 precision / 0.86 recall; `speculative` 0.87 / 0.67 / 0.92 / 0.72; `flare` 0.98 / 0.72 / 0.93 / 0.87. The 16 modes in the table above predate `context_precision`/`context_recall` and have no numbers for them yet (re-run `npm run eval` for a full four-metric table), so these can't yet be ranked against them on those two metrics. `flare`'s 0.98 faithfulness is the highest measured, but its relevancy (0.72) trails `condense`, and it costs 1 + up to 4 extra LLM calls. `raptor` is unevaluated (needs STEP 13 + re-upload).

**Decision: `condense` stays the default (`DEFAULT_RAG_MODE`).** It is within 0.01 of the top scores on both metrics, and top-line differences among the best ~8 modes are inside the noise of a 10-question set judged by a 4B model. Two things the numbers can't show tip it: (1) every eval question is single-turn (`history: []`), but `condense` is the only cheap mode that resolves follow-up/pronoun references in a real chat; `hybrid` (nominally best) embeds the raw question and would regress there. (2) `hybrid` also needs `supabaseScripts.txt` STEP 9. Documented alternates worth choosing deliberately: `hybrid` for keyword/acronym-heavy documents, `multi-hop` for compound questions. Weakest on this doc/model: `graph` (0.70 faithfulness — a 1B model's entity extraction is unreliable), `auto-merging`, `rerank`, `crag` (0.82–0.86) — treat as teaching modes, not production choices. To revisit: re-run with a multi-turn golden set and a larger answering model.

## Guardrails — never do this
- NEVER change the vector dimension from 768 without also updating the `documents` table
  column and the `match_documents` RPC in Supabase — a mismatch silently breaks retrieval.
- NEVER add application-level password hashing — the Supabase `before_insert_or_update`
  trigger handles it via pgcrypto. Adding it in code will double-hash and break login.
- The `User-Id` header is NOT verified auth — it is trivially spoofable. Never treat it
  as a security boundary; always be explicit that this is the current limitation.
- Always add new env vars through `src/app/utils/env.ts` — never call `process.env`
  directly elsewhere in the codebase.
- Keep `src/app/lib/rag-strategies/*` (`condense.ts`, `naive.ts`, and any new strategy)
  as plain LangChain runnable compositions (`RunnableSequence`/`RunnableLambda`/prompt
  templates piped together) — this was a deliberate cleanup, not an oversight. Don't
  reintroduce hand-rolled `async (input) => {...}` orchestration in a strategy file to
  extract `sources` early; instead give the relevant step a `runName` via `.withConfig()`
  (see `retrieval.ts`'s `retrieveAndBuildContext` and `condense.ts`/`naive.ts`'s
  `answerLLM`) and read it out in `api/chat/route.ts` via `chain.streamEvents()`.
- When a new retrieval-side step reuses the `vectorRetrieve` runName (so it can share the
  pipeline visualizer's shared stage copy/shapeStageData case instead of needing its own),
  its output must stay a bare `Document[]` — if the next step also needs the original
  question, thread it via a parallel branch (`{docs: retriever(filter)..., question: new
  RunnablePassthrough()}`, see `contextual-compression.ts`'s `compressRetrieveAndBuildContext`
  in `retrieval.ts`), not by wrapping the retriever in a lambda that returns `{question,
  docs}` — that changes the traced output shape and breaks `shapeStageData`'s `"vectorRetrieve"`
  case for every other mode sharing that name.
